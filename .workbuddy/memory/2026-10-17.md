## 关键实测事实与纠错（已写入 `移植任务书.md` 约定 25–28 与 `哑物品清理任务书.md` §七）
1. **`Properties.durability(N)` 优先于 `Tier.getUses()`**：`TieredItem(Tier, Properties)` 内部是 `Properties.defaultDurability(tier.getUses())`，而 `defaultDurability(int)` **只在 `maxDamage == 0`** 时才调 `durability(int)`。→ 此前文档「`TieredItem` 会覆盖 durability，当前耐久一律 250」的说法是错的（`ItemHakurouken` 的 100 一直生效）。
2. **`releaseUsing` 的 `timeLeft` 是「剩余 tick」**：1.7.10 `onPlayerStoppedUsing` 第 4 参是**已按住 tick 数**，因此原版普遍写 `getMaxItemUseDuration(stack) - usedTime` 才是「按住时长」→ 1.20.1 对应 `getUseDuration(stack) - timeLeft`。反例：`ItemMikoSword` 原版写 `min(72000 - usedTime, 50)`，在 1.20.1 里等价于 `min(timeLeft, 50)`。
3. **`toyosatomimi_sword` 的依赖判断有误**：任务书原写「只需把 `EntityList` 改写为 `EntityType`」，实际原版 `ItemMikoSword` 里那行早已被作者注释，真正用的是 `getCommandSenderName()` + 一组 `instanceof`；而 `EntityDivineSpirit`（小神霊）**整个实体都没迁移**（1.20.1 只有 19 行空 `TileEntityDivineSpirit` 占位 + 单变体 `divine_spirit` 方块）。本轮连带补齐实体 + 渲染器 + 实体注册 + 语言键。
4. **1.20.1 继承链**：`WaterAnimal extends PathfinderMob`（不是 `Animal`）、`Animal extends AgeableMob`、`TamableAnimal extends Animal implements OwnableEntity`（`isTame()`）、`Creeper extends Monster`、`Villager extends AbstractVillager`。
5. **`Entity.setSize` 在 1.20.1 不存在** → 尺寸用 `EntityType.Builder.sized(w, h)`；`isInRangeToRenderDist` → 覆写 `shouldRenderAtSqrDistance(double)`（`getAverageEdgeLength()` → `AABB.getSize()`）；`getCollisionBorderSize` 无对应。
6. **折伞 ribbon 染色故意不做（已知偏差）**：原版双层贴图 `GapFoldingUmbrella_base`（= 1.20.1 的 `gap_folding_umbrella.png`，sha256 相同）+ `GapFoldingUmbrella_ribbon`（未移植），且全工程没有 `ItemColor`/`RegisterColorHandlersEvent`。故 `GapColor` 只影响生成的隙间颜色（`32 + color`），不影响手持图标 —— 与 `remorse_rod` 贴图切换同属「客户端动态贴图」打磨项。
7. **折伞换物不用 `hurtAndBreak`**：耐久尽瞬间 `hurtAndBreak` 会把 stack 清空、来不及换回 `gap` 物品，故照 `ItemCursedDecoyDoll` 的既有写法手工 `setDamageValue(getDamageValue() + 1)`。

## 追加段（同日深夜二）：恋符「Non-Directional Laser」五激光朝向修复 → 提交 0ec5093

用户实测前指定核查（原文）：「在我实测之前，你先检查一下恋符「ノンディレクショナルレーザー」这张spell card是个什么情况。按照原版应该是等距环绕在身边的五个激光，一头指向玩家另一头向外。现在看起来五个激光是形成了一个圆筒。」

- **定位**：符卡本体（`thkaguya-1.20.1/src/main/java/thKaguyaMod/entity/spellcard/THSC_NonDirectionalLaser.java`）、`THShotLib.createLaserB`（`:1359`）、`THShotLib.getVectorFromRotation`（`:440`）与 `EntityTHSetLaser` 的位置算法（`pos + angle * settingLength`，`:44-47 / :81-84`）都与原版逐字一致 → 五条光束确实被摆在半径 1.5 / 抬高 1.0 的圆周上，「环绕」没问题，问题只在朝向。
- **根因**：原版 `EntityTHLaser` **覆写了 `updateAngle()`**（1.7.10 `extract/sources/java/thKaguyaMod/entity/shot/EntityTHLaser.java:75-96`）——从方向ベクトル `angle` 算 yaw/pitch，且整段被 `if(!worldObj.isRemote)` 包住（服务端专用）。移植版漏了这个覆写，直接继承 `EntityTHShot.updateAngle()`（`EntityTHShot.java:220-226`），而基类改用 `getDeltaMovement()` 算。固定激光 `EntityTHSetLaser` 初速度恒为 0（`createLaserB` 传 0.0D/0.0D/0.0D）→ deltaMovement 始终 (0,0,0) → 每 tick 把 yaw/pitch 打成 0 → 五条光束全部指向同一方向、只在位置上围成一圈 = 圆筒。
- **修法**：在 `thkaguya-1.20.1/src/main/java/thKaguyaMod/entity/shot/EntityTHLaser.java` 补回原版覆写（**服务端专用**；客户端 `angle` 恒为 (0,0,0)，若客户端也按 angle 计算会把朝向再次打成 0），yaw/pitch 用 `atan2(angle.x, angle.z)` / `atan2(angle.y, sqrt(x²+z²))`（与 `THShotLib.getYawFromVector`/`getPitchFromVector` 同式）并保留原版的 ±180 折返。顺带修好神枪 GUNGNIR 前 10 tick 的朝向（`specialMotion()` 里 `angle = move; updateAngle();` 原本也走基类归零）。
- **渲染侧证据**：`client/render/shot/RenderTHLaser.java:74-96` 只用 dispatcher 的 `yaw` + `entity.getXRot()`（`Axis.YP.rotationDegrees(yaw)` + `Axis.XP.rotationDegrees(-entity.getXRot())`，**无 180 偏移**），注释已写明「angle 未同步、客户端恒 (0,0,0)，只有 yaw/xRot 会通过生成包与旋转同步到达客户端」→ 修实体朝向即可修好画面；生成包携带的朝向本就正确（构造时 `EntityTHShot` 调 `updateYawAndPitch()` 用 angle 算），问题只是每 tick 被归零。
- **影响面**（`createLaserB` 全部调用点）：`EntityMiniHakkero.java:80/106`（魔炮）、`ItemLaevateinn.java:104/118`（莱瓦汀）、`THSC_Kachoufuugetu.java:60`、`THSC_MoonlightRay.java:35`、`THSC_NonDirectionalLaser.java:34/48`。
- 构建 BUILD SUCCESSFUL in 34s；jar 同步到 mods 目录（两侧 md5 `2ABD4D54C15EBACBC8DF2EE6EC3694B1`）；提交 `0ec5093`（1 file changed, 36 insertions）。
- **事故与修复（文件损坏）**：本文件前一次追加段是 **GBK(ANSI) 编码**写入的 → 整段非法 UTF-8（读取工具报 `invalid UTF-8`，`edit` 报 `binary file`），且文本里的 `\0`/`\v`/`\t`/`\a` 被当成转义序列写成了控制字节 0x00/0x0B/0x09/0x07。修复：按字节边界 9880 切分（前段 UTF-8 + 后段 GBK）重新解码为 UTF-8，再逐个替换控制字节（`\0.75`→`u0.75`、`\v0`→`v0`、`\thkaguya`→`thkaguya`、`\tickCount`→`tickCount`、`\a2ce217`→`a2ce217`），复核控制字节为零。**教训：写 memory/任务书一律用 write/edit 工具，不要在 pwsh 命令里用双引号或 here-string 拼中文文本**（GBK 编码 + 反斜杠转义双重陷阱）。

### 追加段（同日深夜四）—— 第三轮实测：御币弹的真正根因是 EntityType 串到父类

## 追加段（同日深夜十一）：工作台产物修复 —— 成型弹/激光 + 成品可回填（`3c45907`）

**用户实测回报（第四轮批次 2）**：19 弹/3 激光形状与伤害全对、图标默认白 + 工作台定色 + `_2` 高光层正常、弹幕之素可发射、回归全 OK。**唯一问题**：弹幕工作台「出来的还是弹幕之素，有 NBT，但发射依然是普通 tiny 弹」，且「弹幕无法放入」（成品放不回素材槽）；激光工作台同样表现。

**根因**：原版 `ContainerDanmakuCrafting` 的产物是 `new ItemStack(THKaguyaItems.shot_item)` + `setItemDamage(素材的 itemDamage)`（`extract/sources/java/thKaguyaMod/gui/ContainerDanmakuCrafting.java:321-323`），激光是 `laser_item`（`ContainerDanmakuCraftingLaser.java:296-297`）；原版素材槽只认 `shot_item`/`laser_item`（`SlotDanmakuCraftingA.java:60-69`）。移植版把产物写成 `SHOT_MATERIAL` + `setDamageValue(...)`，而 `ItemShotMaterial` 只发白 tiny、完全不读 NBT —— 于是「有 NBT 但发射是 tiny」；素材槽 type 2/5 又只认 `shot_material`/`laser_material`，成品放不回去。

**修法**：
- `thkaguya-1.20.1/src/main/java/thKaguyaMod/init/THKaguyaItems.java`：新增 `SHOT_BY_TYPE`（19 项，顺序同 `ItemTHShot` 的 0-18）/`LASER_BY_TYPE`（middle/short/long）+ `shotItem(int)`/`laserItem(int)`/`shotTypeOf(ItemStack)`/`laserTypeOf(ItemStack)`/`isShotMaterialItem`/`isLaserMaterialItem`；旧 `shot_material` 若带 damage 仍按 damage 取 type（兼容旧存档）。
- `ContainerDanmakuCrafting.recalcResult()`：产物 `new ItemStack(THKaguyaItems.shotItem(THKaguyaItems.shotTypeOf(craftMaterial.getItem(0))))`，删掉 `setDamageValue`。
- `ContainerDanmakuCraftingLaser.recalcResult()`：同上，用 `laserItem`/`laserTypeOf`。
- `SlotDanmakuCraftingA`：type 2 → `isShotMaterialItem`，type 5 → `isLaserMaterialItem`。

**验证**：`BUILD SUCCESSFUL in 43s`（唯一 warning 仍是 `ResourceLocation(String,String)` 废弃）；jar 同步 mods，两侧 md5 `DCFEB208FF5A8B2987AE211D34019431`。提交 `3c45907`（4 files, 73+/6-）。

**教训（已写进铁律 30）**：把「item + damage」拆成 N 个独立 Item 后，**所有造出这个物品的地方都要跟着改**——注册、配方、图标只是第一层，容器/工作台/掉落表/指令产出的 stack 是第二层，漏了就是「做出来的东西不能再用」。
## 追加段（同日深夜十二）：弹幕工作台染色不生效（`fd4f634`）

**用户反馈（第五轮）**：「放入和产出OK了，但是染色功能似乎不大对劲（白色弹幕即使放了红色染料出来还是白色）。其他看起来正常了，修一下」。

**根因**：原版 `ContainerDanmakuCrafting.recalcResult()` 里颜色槽是这样取的 —— `ItemTHShot.sellectbleColor[colorSlotStack.getItemDamage() % 16]`。1.7.10 只有一个 `Items.dye`，`getItemDamage()` 就是颜色（0=墨囊/1=红/2=绿/3=棕/4=蓝/5=紫/6=青/7=淡灰/8=灰/9=粉/10=黄绿/11=黄/12=淡蓝/13=品红/14=橙/15=骨粉）。1.20.1 把染料拆成 16 个独立物品，`getDamageValue()` 恒 0，而移植版还额外只认 `Items.RED_DYE` —— 两道限制叠加，任何染料都命中 `SELECTABLE_COLOR[0] = 7 = 白`，于是「放红染料出白弹」。

**修法**（`fd4f634`，3 files, 35+/5-）：
- `ContainerDanmakuCrafting` 新增 `DYE_BY_LEGACY_META`（16 项，严格按 1.7.10 metadata 顺序：`BLACK_DYE, RED_DYE, GREEN_DYE, BROWN_DYE, BLUE_DYE, PURPLE_DYE, CYAN_DYE, LIGHT_GRAY_DYE, GRAY_DYE, PINK_DYE, LIME_DYE, YELLOW_DYE, LIGHT_BLUE_DYE, MAGENTA_DYE, ORANGE_DYE, WHITE_DYE`）与 `static int dyeColorIndex(ItemStack)`（染料 → `SELECTABLE_COLOR[meta]` 即调色板 0-7，非染料 -1），`recalcResult()` 改用它。
- `ContainerDanmakuCraftingLaser.recalcResult()`：同样改用 `dyeColorIndex`（激光工作台原版同构）。
- `SlotDanmakuCraftingA`：颜色槽 type 3 从「只认红染料」改为 `stack.getItem() instanceof DyeItem`（原版就是任意染料）。

**映射结果**（与原作者 `sellectbleColor[]` 表逐项一致）：墨囊/淡灰/灰/骨粉→白；红/棕→红；蓝→蓝；绿/黄绿→绿；黄→黄；紫/粉/品红→紫；青/淡蓝→水；橙→橙。

**验证**：`BUILD SUCCESSFUL in 39s`；jar 同步 mods，两侧 md5 `DD39894A288366CF5221239858AAF631`；提交 `fd4f634`。

**教训（已写进铁律 31）**：凡是从 1.7.10 搬来的 `damage % N` 读法，都要先问「这个物品在 1.20.1 是不是被拆成 N 个独立物品了」——染料、羊毛、原木、鱼、旗帜、陶片全是这类。
