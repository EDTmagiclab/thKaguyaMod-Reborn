## 五つの難題MOD+ 1.7.10 → 1.20.1 移植可行性分析

**目标 mod**：`五つの難題MOD+ ver2.90.1-1.7.10.jar`（东方Project 同人 mod，Touhou 主题）
**产出**：`移植可行性分析报告.md`（工作区根目录）

### 核心发现
1. **jar 自带原始源码**：`sources/java/thKaguyaMod/`，266 个 `.java`、53,341 行，无反编译痕迹。任务性质从「逆向」变为「API 适配重写」。完整解包在 `extract/`。
2. **无自建网络层**：全仓 0 处 `IMessage`/`SimpleNetworkWrapper`/`ByteBuf`。仅 `NetworkRegistry.INSTANCE.registerGuiHandler`。这是可行性评为「高」的决定性因素——绕开了 1.20.1 移植最贵的网络改版环节。
3. **资源层几乎空白**：资产包仅 1 个 `sounds.json`，0 个 .ogg 文件（readme 说明由玩家自备）。blockstates/models 需从零写，贴图可复用。
4. **硬性前置任务**：23 个非 `client` 包文件直接 import `net.minecraft.client.*`（EntityMarisaBroom、多件 Item、BlockDanmakuCraftingTable 等），1.7 下靠 `@SideOnly` 侥幸工作，1.20.1 服务端会直接崩溃，须用 `DistExecutor` 包装。
5. **`setHealth` 陷阱**：18 处直接赋值，1.20.1 需改 `Attribute` 读写，否则客户端/服务端血量不同步。

### 规模与估算
- 270 class / 64 物品 / 2 方块 / 1 TE / 109 配方 / 45 实体 / 49 渲染器 / 4 套 GUI
- 事件仅 3 类（`FMLPreInitializationEvent`、`LivingDeathEvent`、`@SubscribeEvent`），改造面收敛
- 工作量：约 32–47 人天，单人全职 2–3 个月
- 建议渐进路线，先跑通「1 实体 + 1 GUI」完整链路再批量迁移

### 环境备注
本机网络代理（127.0.0.1:6232）TLS 握手失败，Maven Central / GitHub Releases 下载均中断（curl 35 / WinError 10053），Vineflower 反编译器未能下载。已改用 `javap` + 源码直读完成分析，无实质影响。
`git clone` 对 GitHub / gh-proxy.org 同样因 TLS 中断失败。**WebFetch 工具走不同网络路径，可用**，适合逐文件读取 GitHub raw 内容。

## l89669/THKaguyaModRe-fork（标称 1.12.2）分析

**仓库**：`github.com/l89669/THKaguyaModRe-fork`（已克隆至 `thkaguya-1.12.2/`）
**产出**：`1.12.2移植版分析报告.md`

### 核心结论：假移植，净收益为零
1. **逐字节比对：259 / 266 文件与原版 1.7.10 完全相同**（97.4%），包结构 21 个包一个不少，代码量 267 文件 / 53,348 行 vs 原版 266 / 53,341。
2. **唯一真实改动仅 `CommonProxy.java` 一处**：`THKaguyaConfig.entityIdXXX` 硬编码 → `EntityRegistry.findGlobalUniqueEntityId()` + `nextID++`。其余 7 个"差异文件"中 3 个是纯CRLF/LF 换行符差异（`EntitySilverKnife` 两版均 937 行，`diff <(tr -d '\r')` 为空）。
3. **`THKaguyaCore` / `THKaguyaConfig` / `THKaguyaItems` / `THKaguyaRecipe` / `THKaguyaBlocks` 全部零改动** —— 恰是 1.7→1.12 必须大改的部分。
4. **附带 jar 在 1.12.2 上跑不起来**：常量池分析显示 271 个 class 中**53 个仍引用 `net/minecraft/util/MovingObjectPosition`（1.7.10 路径），0 个用 1.12.2 的 `util/phys` / `util/math` 新包**。放入 1.12.2 会 `NoClassDefFoundError`。仅 `findGlobalUniqueEntityId` 是 1.12.2 特征。
5. **升级成本与基于原版完全相同（32–47 人天），净收益 ≈ 0**。那唯一改动（实体 ID）在 1.20.1 已无关——1.20 用 `EntityType.Builder` + `DeferredRegister`，不再需手动分配 ID。
6. 仓库无 build.gradle / gradle wrapper，目录为非标准 `java/`，需重建构建配置。

### 方法论教训（重要）
**不能仅凭文件数与行数判断移植进度。** 本仓库 267 文件 / 53,348 行，规模与原版几乎一致，看起来是完整移植，实际 97.4% 内容未动 —— 是「换名不换实现」的典型反面案例。必须做逐字节 `cmp` 比对 + 检查核心注册类是否改动 + 对编译产物做常量池版本特征分析。

### 三版横评
| 起点 | 内容 | 升级 1.20.1 成本 |
|---|---|---|
| **原版 1.7.10** | 266 文件 / 53,341 行 | **32–47 人天（最佳）** |
| l89669（标称 1.12.2） | 与原版 97.4% 相同 | 32–47 人天（收益 ≈0） |
| rikka0w0（实为 1.14.4） | 35 文件 / 6,136 行 | 37–54 人天（更贵） |

**结论不变：以原版 1.7.10 自带源码为唯一基线。**

## 崩溃检修（第二次）：ResourceLocation 大写路径导致启动崩溃

**用户测试**：替换渲染修复版 jar 后 → 游戏**直接启动不了**（连标题画面都进不去）。
**崩溃根因**（crash report）：`ExceptionInInitializerError` → `ResourceLocationException: Non [a-z0-9/._-] character in path of location: thkaguya:textures/shot/Shot.png`，位于 `RenderTHShot.<clinit>`。

### 原因
实体渲染器里硬编码的贴图路径沿用了原版 camelCase 文件名（`Shot.png`、`FairyTexture_0.png`），但 1.20.1 的 `ResourceLocation` 路径**只允许小写字母 `[a-z0-9/._-]`**，大写字母直接抛异常。且渲染器 `ResourceLocation` 是 `static final` 字段，类加载时（`<clinit>`）就触发 → 资源重载阶段崩溃 → 游戏启动失败。

### 修复
1. 批量重命名 30 张实体贴图为全小写（shot 26 张 + mob 4 张），用 Python 两步 rename（Windows NTFS 大小写不敏感，需先改中间名 `*.tmp` 再改目标名）。
2. 改两处代码引用：`RenderTHShot` 的 `textures/shot/shot.png`、`RenderTHFairy` 的 `textures/mob/fairytexture_0.png`。
3. 全资源目录排查确认 0 个含大写字母的文件。

### 经验教训（重要，写入 MEMORY.md）
- **Minecraft 1.13+ 所有资源标识符（ResourceLocation）路径必须全小写**，含贴图/模型/lang/配方。文件名本身也要小写（资源加载大小写敏感）。这是从 1.7.10（允许 camelCase 贴图名）迁移到 1.20.1 的**系统性坑**，不是个案——凡是沿用原版 camelCase 资源名的地方都会踩。
- `static final ResourceLocation` 在类加载时就校验路径合法性，一旦含大写/非法字符，会在资源重载阶段（而非实体生成时）就崩溃，表现为「游戏启动不了」而非「刷实体崩」。
- 用户游戏目录：`F:/mc/versions/newserver/.minecraft/versions/1.20.1-Forge_47.4.28/mods`（PCL 启动器，非默认 .minecraft）。已直接把新 jar 覆盖到该目录。

## 检修：妖精「站着不动、不发弹」—— 5 个连锁 bug

**用户反馈**：妖精能正常刷出（渲染修复生效），但不发弹、不攻击、站着不动。

### 根因（5 个连锁 bug，全在实体 tick/配置链上）

1. **`getTarget()` 无限递归**：`return this.getTarget()` 应为 `return super.getTarget()`。danmakuLevel>0 时会 StackOverflow。
2. **时停检查死锁（核心）**：`tick()` 开头 `if(tickCount <= lastTime) return`。原版 1.7.10 里 `ticksExisted` 由 World 框架在 `onUpdate()` **之前**递增（`World.updateEntityWithOptionalForce` 里 ticksExisted++），所以 first tick 时 ticksExisted 已是 1 > lastTime(0)。而 1.20.1 的 `tickCount` 在 `super.tick()`→`baseTick()` **内部**递增，第一次 tick 时 tickCount=0 <= lastTime=0 → 永久冻结，实体连 super.tick() 都不执行。**这是「站着不动」的直接原因。**
3. **`THKaguyaConfig.load()` 从未调用**：danmakuLevel 静态字段恒为 0，tick 里 `if(danmakuLevel<=0) setTarget(null)` 每 tick 清空目标。修复：注册 `ModConfigEvent.Loading`/`Reloading` 监听（包路径 `net.minecraftforge.fml.event.config.ModConfigEvent`，不是 `fml.config`）。
4. **妖精构造函数漏 `setPattern()`**：danmakuPattern/speedRate/danmakuSpan/shotForm/shotColor 全默认 0，弹速=0。原版构造函数有 `setPattern(rand.nextInt(pattern.size()))`。
5. **缺 attackCounter 归零**：原版 `if(attackCounter > danmakuSpan) attackCounter = 0` 在 EntityTHFairy.onUpdate 的 super.onUpdate() 之后，移植版漏了，导致 attackCounter 只增不减，danmakuPattern 里 `if(attackCounter>0) return` 永远触发。

### 修复
- `EntityDanmakuMob`：getTarget→super.getTarget；tick() 移除时停冻结、无条件 super.tick()，末尾加 attackCounter 归零。
- `EntityTHFairy`：构造函数加 setPattern（pattern 空则跳过，避免 nextInt(0)）。
- `THKaguyaCore`：注册 ModConfigEvent 监听调 load()；commonSetup 里 `DanmakuPatternRegistry.setDanmakuPattern()`（依赖 danmakuLevel，须在配置加载后）。
- `DanmakuPatternRegistry.setDanmakuPattern()` 依赖 danmakuLevel 走 case 分支，default 分支（danmakuLevel=0）注册的是 speed 0.0F 占位图案——所以配置加载是整条链的地基。

### 经验教训（写入 MEMORY.md）
- **1.7.10 的 `ticksExisted` 与 1.20.1 的 `tickCount` 递增时机不同**：前者 World 框架在 onUpdate 前递增，后者在 super.tick() 内递增。任何依赖 `tickCount <= X` 做"时停/冻结"判断的 1.7 代码，直接搬到 1.20.1 会第一次 tick 就死锁。弹体 EntityTHShot 也有同样的 lastTime 模式，但它的 lastShotMotion 在构造函数已初始化为初速度，且没有"<= 冻结 return"，所以没踩坑。
- **配置值必须显式 load()**：ForgeConfigSpec 只是声明，静态字段不会自动同步，需监听 ModConfigEvent。

## 检修：妖精「不索敌 + 弹幕贴图错乱」

**用户反馈**：妖精会发弹了（上一轮修复生效），但①不索敌（不追踪玩家）②不论模式都稳定节奏发弹 ③弹幕贴图「所有贴图一起出现」。

### 根因与修复

**① 不索敌 = 缺移动决策逻辑**。原版 EntityDanmakuMob.onUpdate 末尾有：
- 迷失目标时 `move(随机方向, getSpeed(), 30)`
- 有目标时按距离 `moveBack/moveForward` 保持攻击距离
- 飞行高度调整（motionY）
移植版漏了整段。修复：在 tick() 的 target 处理后补上 `moveTimer<=0` 时的移动决策（`distanceTo` + `getDanmakuSpeed()`），并给妖精加 `setNoGravity(true)`（原版飞行怪靠 motionY 抵消重力，1.20.1 需显式 noGravity，否则落到地面）。

**③ 弹幕贴图错乱 = 原版是「形状→贴图文件 + 颜色→UV 子图」的两级选择**。原版：
- 每种形状一张 sprite sheet（如 SmallShot.png 128×16 = 8 张 16×16 横向排布，8 色）
- `renderNormalShot` 用 `u1 = color/8F, u2 = (color+1)/8F` 横向选第 color 格子图
- 单张图（Kunai/Star/Laser 64×32 等）用全图 + colorR/G/B 顶点染色
我的简化版统一用 Shot.png（256×256，原版 getEntityTexture 根本没返回它）+ UV 全图 → 整张图集被画出来 = 「所有贴图一起出现」。

修复：重写 RenderTHShot——`getTexture(form,color)` 按形状选贴图（16 种形状→对应文件），`isEightColorSheet(form)` 判断 8 色横向（SMALL/TINY/MEDIUM/PEARL/CIRCLE/HEART/TALISMAN/BIG，即宽/高==8），8 色用 color/8 UV，单张图全图+染色。KNIFE 用 8 张独立 silverknife_*.png（按 color 选文件）。

### 关键结论
- 原版弹体渲染是「形状决定贴图文件，颜色决定 UV 横向子图」，sprite sheet 内已含 8 色变体，不需 GL 染色（renderNormalShot 无 setColorRGBA）。
- 颜色常量：RED=0,BLUE=1,GREEN=2,YELLOW=3,PURPLE=4,AQUA=5,ORANGE=6,WHITE=7（DanmakuConstants）。
- colorR/G/B 染色表（单张图用）：R{224,0,0,224,224,0,255,255} G{0,0,224,224,0,224,128,255} B{0,224,0,0,224,224,0,255}。

## 检修：弹幕无伤害

**用户反馈**：弹幕能发、能看见，但命中无伤害。

**根因**：`EntityTHShot.damageRate` 字段默认 0.0F，命中时没有重置。原版 `onImpact`（1051 行）在命中瞬间才 `damageRate = 1.0F`，再算 `getShotDamageWithDifficulty() * damageRate`。我移植的 `onImpact` 直接 `getShotDamageWithDifficulty() * damageRate`，漏了 `damageRate = 1.0F`，导致 `shotDamage * 0 = 0` 永久无伤害。

**修复**：onImpact 命中分支开头补 `damageRate = 1.0F;`。

**教训（写入 MEMORY.md）**：`float` 字段默认 0，原版「命中时才赋值的倍率字段」直接搬过来、又不补赋值，会静默把伤害/数值归零。移植时凡是对数值做乘法的字段，务必核对它的默认值与初始化时机。

**遗留**：原版还有 `damageRateEx`（对 DanmakuMob 的 isYoukai/isFairy/isPhantom 种族 2 倍伤害），属于阶段 3d 完整伤害系统细节，暂未补。

## 检修：弹幕仍无伤害 + 补弹体生命周期

**用户反馈**：弹幕仍无伤害；妖精会拉开距离。

### 排查结论
逐项对照原版确认伤害链路**代码正确**：
- 弹体方向 `getVecFromAngle`（标准 yaw/pitch 转向量）
- 碰撞检测 `hitEntityCheck`（`boundingBox.addCoord(angle).expand(hitSize)` ↔ `getBoundingBox().expandTowards(angle).inflate(hitSize)` 语义一致）
- 命中处理 `onImpact`（damageRate=1.0F 已补、indirectMagic 伤害源正确）
- 伤害值 `DAMAGE[]` 非 0（SMALL 2.4 / CIRCLE 2.0 / TINY 1.0）

**「无伤害」最可能 = 创造模式**（用户「东西都能拿出来」暗示创造模式；Minecraft 创造模式玩家免疫实体伤害）。

**「妖精拉开距离」= 正常**：原版 `moveBack` 在 `toTargetDistance < attackDistance` 时后退，是「保持攻击距离」的弹幕机设计。

### 补修：弹体生命周期（2 个遗漏）
1. `EntityTHShot.tick()` 没调用 `super.tick()` → tickCount（弹体年龄）不递增。
2. `animationCount` 不递增 → 弹体永不超时消失（`getAnimationCount() > getShotEndTime()` 永远 false）。

修复：tick() 开头 `super.tick()`；animationCount 逻辑还原原版——`>=0` 时 `setAnimationCount(tickCount)`（跟踪弹体年龄，用于超时消失），`<0` 时 `+1`（延迟倒计时，延迟阶段不移动）。

### 关键教训（写入 MEMORY.md）
- 重写 `Entity.tick()` 必须 `super.tick()`，否则 `tickCount` 不递增，依赖 tickCount 的时间逻辑（超时/动画/时停）全部失效。
- 弹体的「形状选贴图 + 颜色选 UV」已正确，颜色常量 RED=0..WHITE=7。

## 弹幕无伤害：根因定位（canBeCollidedWith 语义变化）

**日志定位**：`candidate=ServerPlayer canCollide=false` → 玩家被碰撞检测过滤掉，`onImpact` 从未触发。

**根因**：`Entity.canBeCollidedWith()` 在 1.20.1 **默认返回 false**（字节码 `iconst_0; ireturn`），且 `LivingEntity`/`Player`/`ServerPlayer` 都**没有重写**它。所以玩家 `canBeCollidedWith()` = false，被 `if(!e.canBeCollidedWith()) continue` 过滤。

**1.7.10 的 `canBeCollidedWith()` 等价于 1.20.1 的 `isPickable()`**（`LivingEntity.isPickable()` = `!isRemoved()`）。

**修复**：`!e.canBeCollidedWith()` → `!e.isPickable()`。

**教训（写入 MEMORY.md）**：`canBeCollidedWith()` 是 1.7→1.20 的**语义陷阱**——同名方法含义完全不同。投射物命中检测必须用 `isPickable()`，不是 `canBeCollidedWith()`。

**日志基础设施**：MC 1.20.1 调试日志用 `LogUtils.getLogger()` + slf4j（System.out 不落盘）。
