## 首次联机实测 → 修复扫帚 rubber-band（commit 60842f8）

**实测证据**（`run/server_live.log`，玩家 `H0uraisanKaguya` 12:07:29 进服、12:09:59 退出）：
```
[12:08:15] entity.thkaguya.marisa_broom (vehicle of H0uraisanKaguya) moved wrongly! 0.25921756186946254
[12:08:19] ... moved wrongly! 0.572830705804563
[12:08:19] ... moved wrongly! 0.7383828517257882
[12:08:26] ... moved wrongly! 0.2628617766695811
```
- `vehicle of <player>` 这个措辞只有服务端把该玩家认作载具的 controlling passenger 才会打印 → **`getControllingPassenger()` 修复已生效**，客户端 WASD 输入确实驱动了载具。
- 但同时服务端在拒绝位移 → rubber-band。

**根因**：服务端也在跑 `tick()` 的自走段。`level().isClientSide == false` → 键位不读、`move_up` 保持默认 `true` → 服务端自己算出一套 motion + `setDeltaMovement` + `move()`，与客户端上报位置漂移超阈值。

**javap 反查的判定链**（`ServerGamePacketListenerImpl.handleMoveVehicle`，与 `handleMovePlayer` 不同）：
```
d10,d12,d14 = clamp(client x,y,z)
d0,d1,d2    = 服务端 entity x,y,z
d26 = (client-server) 平方距离
if (d26 > 0.0625)  → wrong = true; warn("{} (vehicle of {}) moved wrongly! {}", ..., Math.sqrt(d26))
entity.absMoveTo(client...)                              // 先接受
if (noCollision(bbox.deflate(0.0625)) && (wrong || !noCollision(新位置)))
    { entity.absMoveTo(服务端旧位置); send(ClientboundMoveVehiclePacket); return; }   // ← rubber-band
```
即容忍度是 **0.0625 平方 = 0.25 格**（日志里的 0.259/0.573/0.738 是开方后的真实格数）。
另有 `> 100.0` 的 "moved too quickly" 分支（更宽松，不触发）。

**修法**（只改服务端侧，客户端输入逻辑不变）：
1. `this.setDeltaMovement(mx, my, mz)` → 包进 `if (this.isControlledByLocalInstance())`。理由：否则服务端写 delta 会被 `ServerEntity.sendChanges()` 经 `ClientboundSetEntityMotionPacket` 广播回客户端，客户端 `lerpMotion` 把操舵速度覆盖掉（第二处漂移源）。
2. `this.move(MoverType.SELF, ...)` → 改为 `if (!(getFirstPassenger() instanceof Player) || isControlledByLocalInstance())`。
   - 无乘客 → 双方照旧自走（保留原行为）
   - 本地客户端操控 → 自己 move（操舵即生效）
   - 服务端 / 他人客户端操控 → 不自走，位置由 `handleMoveVehicle` 的 `absMoveTo` + `move(MoverType.PLAYER, delta)` 反映

**已核验 API**：`Entity.isControlledByLocalInstance()` public（`getControllingPassenger() instanceof Player` → `player.isLocalPlayer()`，否则 `isEffectiveAi()`）；`Entity.isEffectiveAi()` = `!level.isClientSide`；`Player.isLocalPlayer()` public。

## 第二次联机实测 → 扫帚 WASD 真正生效（commit 8d22dc6）

**第二次会话**（`run/server_live2.log`，玩家 12:16:25 进服 / 12:17:51 退出）：
- **`moved wrongly` 彻底消失** → 服务端不再与客户端抢位置（60842f8 生效）。
- 但玩家反馈「**完全动不了，还不如之前**」→ 两端都不动。

**根因（重要教训：我上一轮对「功能债」的判断太浅）**：
```
if (this.level().isClientSide && this.isEmpty)  // A: 插值分支
else                                            // B: 读键位 + 自走分支
```
`isEmpty` 的 setter（原版 `func_70270_d` / 移植版 `setIsEmpty`）**在原版和移植版中都没有任何调用点**，恒为 `true`：
- 客户端永远进分支 A（插值）→ 分支 B 里的 `isPushKeyUp()` 等客户端专用键位读取**从未执行**；
- **原版 1.7.10 亦如此**（作者写了 `isPushKeyUp()` 但够不到它）；
- 所以「鼠标能控方向、WASD 无效」的真身是：**服务端**在分支 B 里用 `move_up` 默认 `true` 自走，方向取乘客的 yaw/pitch → 看起来像鼠标转向。
- 我上一轮把 `return false` 桩当成根因是错的：那个桩其实与原版实际行为等价。

**修复（三步，commit 8d22dc6）**：
1. 分支 A 条件：`this.level().isClientSide && this.isEmpty` → `this.level().isClientSide && !this.isControlledByLocalInstance()`
   —— 语义变成「本实例不是操縦権威就插值，是操縦権威就读键位自走」。
   本地玩家骑行 → `isControlledByLocalInstance()`=true → 进分支 B → 读 WASD。
   无乘客 / 他人箒 / 服务端 → 行为与传统一致（无人×客户端仍走插值）。
2. `lerpTo()` 加护栏：`if (isControlledByLocalInstance() && !teleport) return;`
   —— 防止服务器常规位置包把每 tick 算出的移动清零（`lerpTo` 会把 `setDeltaMovement(velocityX..)` 写成 0）。
   已 javap 确认 rubber-band 走 `ClientboundMoveVehiclePacket` → `ClientPacketListener.handleMoveVehicle` → **`absMoveTo`**（不是 `lerpTo`），故不受该护栏影响。
3. `isEmpty` 字段补注释，标明其为恒 true 的遗留标志（现仅用于 `lerpTo` 决定插值步数）。
